# Feature: 티어 내 가중치 ± (tier-adjustment)

**단계**: 정적 웹 · **선행**: M1

## 문제
같은 티어 안에서도 우열이 있는데 지금은 모두 같은 점수라서 동점이 많이 생기고 미세한 판단을 반영할 수 없다.

## 목표 / 비목표
- 목표: 같은 티어 안에서 대상자에게 +1/-1 보정을 주되, 티어 순서가 뒤집히지 않게 한다.
- 비목표: 티어를 넘는 보정, 평가자 간 보정 조정.

## 요구사항
- 평가 페이지: 티어 안의 대상자 칩에서 보정(+/-)을 줄 수 있다. 보정값이 칩에 표시된다.
- **역전 불가**: 어떤 보정을 줘도 한 티어의 최저 점수가 바로 아래 티어의 최고 점수보다 높다 (예: S=4, A=3이면 A의 + 보정은 3을 넘되 4에 닿지 않는 범위까지).
- 허용 범위를 넘는 보정은 입력 단계에서 막는다.
- 보정은 총점에 더해진다. 동점 처리(S 개수 우선)와 공동 순위는 M1과 동일.
- 티어를 옮기면 해당 대상자의 보정은 초기화된다 *(기획자 제안)*.
- JSON 내보내기/가져오기에 보정이 포함된다.

## 완료 기준
- 어떤 보정 조합에서도 티어 순서(S > A > B > C)가 뒤집히지 않는다. 자동 점검으로 경계 케이스를 검증한다.
- 보정을 쓴 평가에서 동점이 실제로 줄어든다.
- M1(그리고 이전에 끝낸 feature)의 데이터가 그대로 열린다.

## 기술 방식
- 데이터: 기존 `placements`는 건드리지 않고 별도 `adjustments: { c1: { s1: 1 } }` 맵을 추가한다. 마이그레이션이 필요 없다 *(기획자 판단)*.
- 점수 = 티어 점수 + 보정 단위 × 보정값.
- 역전 불가 보장: 인접 티어 점수 간격 안에서만 보정이 움직이도록 보정 단위와 허용 범위(±N)를 점수표 간격에서 계산한다. M1의 기준별 점수표를 쓰므로 간격은 기준마다 다를 수 있고, 보정 범위도 기준별로 계산한다.
- 보정값이 허용 범위를 벗어나는 입력은 `core.js`에서 거부한다 (JSON 가져오기 검증 포함).

## 테스트
- 모든 허용 보정 조합에서 "한 티어의 최저 점수 > 바로 아래 티어의 최고 점수"가 성립한다 (경계 케이스 fixtures + 전수 점검).
- 보정이 있을 때도 동점 처리(S 개수 우선)와 공동 순위가 동일하게 동작한다.

## 기획자 판단 / 열린 질문
- **보정 폭(단위와 허용 횟수)**: 착수 시 정한다. 점수 간격이 1인 기본 점수표에서 "±1"이 한 단계 전체를 뜻하면 역전이 생기므로, 보정 단위는 간격보다 작아야 한다.
- 티어 이동 시 보정 초기화.
