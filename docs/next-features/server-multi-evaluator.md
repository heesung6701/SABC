# Feature: 서버 확장 · 다중 평가자 (server-multi-evaluator)

**단계**: DB 연동 웹 (Supabase + DB, 호스팅은 Vercel 검토) · **선행**: M1 (정적 웹 feature를 먼저 끝냈다면 그 필드도 서버에 반영)

## 문제
한 사람의 의견만 반영돼서 여러 평가자의 평가를 모을 수 없고, 데이터가 브라우저에 갇혀 있다.

## 목표 / 비목표
- 목표: 평가자 여러 명이 각자 로그인해 평가하고, 합산 순위를 본다.
- 비목표: 관리자/일반 권한 구분 ([admin-evaluator-split](admin-evaluator-split.md)), Android 앱 ([android-app](android-app.md)), 실시간 동시 편집 표시.

## 요구사항
- 로그인한 평가자별로 배치(와 이미 끝낸 feature의 보정 등)를 서버에 저장한다.
- 한 평가자가 다른 평가자의 배치를 덮어쓰거나 수정할 수 없다.
- 결과 페이지: 평가자별 결과와 합산(평균 또는 합계) 순위를 모두 볼 수 있다.
- 평가자별 진행률(배치/전체)을 볼 수 있다.
- M1의 JSON 내보내기 파일을 서버로 가져오는 경로를 제공한다.
- 여러 번의 평가(행사)를 구분해서 만들 수 있다 *(기획자 제안: 지금까지는 평가 하나뿐이었음)*.

## 완료 기준
- 평가자 2명 이상이 각자 평가하고, 합산 순위가 평가자별 결과에 맞게 나온다.
- 한 평가자가 다른 평가자의 배치를 바꾸지 못한다.
- M1에서 내보낸 JSON을 가져와서 같은 결과가 나온다.

## 기술 방식
- 클라이언트: 바닐라 유지. Supabase JS 클라이언트를 CDN 스크립트로 로드 (빌드 없음).
- 인증: Supabase Auth. 평가자 식별은 `evaluatorId`.
- 저장소 교체: M1의 `store.js` 인터페이스를 유지하고 `localStorage` 구현과 Supabase 구현을 바꿔 끼운다.
- 테이블(제안): 평가(evaluation), 대상자, 기준(이미 끝낸 feature의 루브릭·점수 포함), 평가자, 배치(평가자·기준·대상자·티어·보정).
- 접근 제어: Row Level Security로 평가자는 자기 배치만 쓸 수 있다.
- 합산: 평균 또는 합계. 순위 계산은 클라이언트 `core.js`를 유지할지 DB 뷰/함수로 옮길지 이 feature에서 결정한다 (Android와의 중복 제거 관점).
- 이전 경로: M1의 JSON 가져오기 검증 함수를 재사용해 JSON 파일을 서버로 올리는 가져오기 버튼.

## 테스트
- 평가자 2명의 합산 순위가 fixtures와 일치한다.
- 평가자 A가 평가자 B의 배치를 쓰기/덮어쓰기 하면 거부된다 (RLS).
- JSON 가져오기 → 서버 저장 → 결과가 M1 결과와 같다.

## 기획자 판단 / 열린 질문
- 합산은 평균을 기본으로 한다 (평가자 수가 달라도 비교 가능). 합계도 선택 가능한지는 확인 필요.
- 일부 평가자가 아직 끝내지 않았을 때: 끝낸 평가자만 합산하고 완료 인원을 표시한다 *(M1의 "전부 배치해야 결과 확인" 규칙을 평가자 단위로 적용)*.
- "평가"(행사) 단위를 도입할지.
- **Vercel의 역할**: (a) 웹 호스팅을 GitHub Pages에서 옮기는 용도, (b) 서버리스 함수가 필요할 때 쓰는 용도. Supabase만으로 충분하면 호스팅 이전만 한다고 가정했다.
- 순위 계산 위치: 클라이언트 유지 vs DB 계산.
